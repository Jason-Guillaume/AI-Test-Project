# Security Testing Phase 1 需求说明

给 Claude Code 的实现需求。架构、表结构、接口和文件清单以 `docs/security-testing-phase1-dev-plan.md` 为准。本文只规定要做什么、不做什么、怎样算完成。两份文档冲突时，以开发计划里的复用边界和安全限制为准。

---

## 1. 背景

测试开发平台已经具备项目权限、API Catalog、业务管理、ApiRequestExecutor、TestCaseExecutor、TestRun、断言、变量解析、Fixture、Data Factory、Mock、Agent、报告、脱敏和出站白名单。

本阶段要在这套执行体系上增加接口安全变异：从一条正常请求出发，按策略生成认证、越权、参数、重放和业务状态变异，执行后给出可解释的疑似问题。它不是渗透测试平台。

## 2. 目标

用户选择一条已经能成功执行的用例或一个已登记接口，勾选安全策略，先看到将生成多少条安全用例，确认后才保存。执行时先验证基线请求，基线失败就停止判断。基线成功后只改请求的指定部分，经现有 HTTP 执行器发出，按安全期望判定，并把疑似问题写成独立的 Security Finding，进入现有 TestRun 和报告。

一句话：安全模块只负责「改请求」和「解释结果」。发请求、造数、Mock、跑计划、出报告仍用现有模块。

## 3. 用户与权限

平台项目角色沿用现有顺序：viewer、member、editor、owner、平台管理员。`editor` 在界面上叫「项目管理员」。跨项目资源一律 404。

| 谁 | 能做什么 |
|---|---|
| viewer | 查看策略、安全用例、执行结果、Finding、报告里的安全摘要 |
| member | 预览并确认生成安全用例，执行安全测试，确认高风险用例 |
| editor、owner、平台管理员 | 管理本项目自定义策略和规则，修改预发环境开关，确认、误报、忽略、解决 Finding |

被测系统的 Token 来自 Fixture 输出，不是本平台登录 JWT。安全模块不签发 Token，不修改平台用户角色。

## 4. 范围

### 4.1 要做

1. 安全策略：系统内置模板可查看，项目可新增结构化自定义策略，可启用或停用。
2. 变异规则：字段、位置、算子、期望和严重级别都是结构化配置。不允许脚本。
3. 变异引擎：输入基线请求和规则，输出变异后的请求和变异说明。引擎自己不发 HTTP。
4. 认证变异：去掉 Token、空 Token、非法 Token、畸形 Token、错误认证方案。
5. 授权变异：换用户、换被测业务项目、降低权限、更换资源所有者、IDOR。
6. 参数变异：按 API Schema 删除必填、空值、类型错误、0、负数、越界、非法枚举、非法格式、超长字符串。没有 Schema 的字段不自动乱改。
7. Header 变异：删除、置空、非法值、Content-Type 改变、认证头改变。
8. 方法变异：只测试策略允许且接口未登记的方法，不把所有方法都打一遍。
9. 重放：同一请求重复 2 或 3 次，检查是否产生新的业务结果。
10. 重复提交：和重放共用执行循环，但只对创建、提交、支付或已标记幂等的业务动作生成。
11. 业务状态绕过：用业务配置里的终态数据，再次调用该动作。
12. 流程跳步：直接执行流程中靠后的一个业务动作，不重写业务流程执行器。
13. 安全执行：基线验证、变异、执行、安全断言、结果、Finding。
14. 安全用例：引用基线用例，不复制一整份基线内容。
15. Agent：识别安全测试意图，生成计划，必须等人确认后才保存和执行。
16. 报告：现有测试报告增加安全摘要和最重要的几条 Finding。
17. 前端：测试管理下增加「安全测试」，页内用 Tab 看概览、策略、用例和发现。

### 4.2 不做

本阶段不实现 SQL 注入、XSS、命令注入、SSRF 探测、XXE、RCE、文件上传攻击、口令爆破、字典攻击、端口扫描、ZAP、Burp、mitmproxy、页面扫描、移动扫描、SAST、DAST、SCA、密钥扫描、Chaos 和任意脚本。

这些类别可以出现在枚举里并保持关闭。执行到它们时拒绝，不携带攻击载荷。

也不做：

- 另一套 HTTP 客户端、TestRun、报告、权限、Agent 或变量解析。
- 自动创建缺陷。Finding 先独立存在，转缺陷只预留，不实现。
- 伪造过期 JWT。只有 Fixture 已经提供过期 Token 时才允许使用。
- Mock 的序列响应。Mock 仍是一次用例一个静态场景。
- 在安全模块里创建用户、项目或任务。缺数据就判为无法下结论。
- 生产环境的安全变异。没有管理员开关可以打开。

## 5. 业务规则

### 5.1 基线

优先使用一条已经成功执行过的普通用例作为基线。也可以从 API Catalog 的示例值或业务动作绑定组装，但缺必填示例时不能当基线。

用户手写请求时，只能改已登记接口的路径参数、查询、头和正文。地址仍由当前环境拼出。用户不能提交任意 URL 让系统去访问。

执行安全用例时，先发一次基线请求。基线不成功，则本条结果为「无法下结论」，原因是基线失败，不再变异，不产生 Finding。

### 5.2 变异

每次变异必须留下说明：改了哪里、原来是什么、改成什么。Token、口令和 Cookie 落库前脱敏。

认证类期望通常是 401 或 403。参数类期望通常是 400 或 422。越权类期望是 403 或 404。重放和重复提交期望是不产生新的业务结果。

返回码本身不够。200 只在「本应拒绝或本应校验失败」时构成疑似问题。500 记为未处理的服务器错误，严重级别为中，不直接叫漏洞。无法从响应判断时，结果是无法下结论，不建 Finding。

结果只用这五种：通过、疑似问题、执行失败、无法下结论、跳过。不使用「已确认漏洞」作为自动结果。

### 5.3 越权数据

IDOR、换用户、换项目所需的另一个用户、另一份资源、另一个被测项目，都来自 Fixture 输出。解析不到就跳过并说明缺 Fixture。禁止用随机数、当前 ID 加一、或平台自己的项目 ID 去猜。

平台里的项目 ID 和被测系统正文里的项目 ID 是两回事。变异被测项目字段时，只能替换 Fixture 给出的业务项目值。

### 5.4 重放与脏数据

重放次数只能是 2 或 3，间隔不超过 5 秒。创建、支付、重复提交和终态写操作默认是高风险。高风险用例未经成员确认，不发出请求，结果为跳过。

系统不保证能自动删掉重放多出来的业务数据。清理仍只做 Fixture 声明过的清理。

### 5.5 环境

开发、测试环境默认允许。预发和名字无法识别的环境默认不允许，项目管理员可以为本项目打开预发。生产环境名，以及出站目标已标记为生产的地址，一律不允许，请求不能发出。

### 5.6 Finding

只有「疑似问题」才生成 Finding。同一接口、同一变异、同一字段上未关闭的 Finding 不重复插入，只增加重复次数。

状态有：待处理、已确认、误报、已解决、已忽略。状态变更需要项目管理员。误报不会永久挡住以后的新发现，但新记录要带上上次的人工结论。

严重级别由固定规则计算：无 Token 仍能访问需要认证的接口为高；跨用户读到对方资源为严重；参数错误导致 500 为中。不允许模型单独决定级别。

## 6. 与现有模块的关系

安全用例仍是一条 `case_type = SECURITY` 的测试用例，因此能进入套件、计划、TestRun 和报告。基线用例、策略、规则、期望和风险确认放在安全扩展数据里，不给现有用例表加字段。

一次执行仍是：准备 Fixture、激活 Mock、执行用例、关闭 Mock、清理 Fixture。安全分支插在「执行用例」内部。非安全用例的行为保持不变。

执行记录的状态仍使用现有的通过、失败、跳过、错误。细粒度安全结论另存。对应关系：

- 通过 → 用例通过
- 疑似问题 → 用例失败
- 执行失败 → 用例错误
- 无法下结论、跳过 → 用例跳过

报告继续统计原有通过率，并额外展示安全用例的五种结果和 Finding 数量。

Agent 可以选定策略和目标，不能生成脚本，不能绕过白名单，不能自己确认高风险，也不能自己把 Finding 标成已解决。计划生成后必须暂停，等人确认才写入用例；执行前必须再确认环境和用例。

## 7. 页面

在「测试管理」下增加一个菜单「安全测试」，不要再拆成四个侧栏入口。页面内四个 Tab：

- 概览：接口数、已覆盖接口、安全用例数、最近执行、未关闭 Finding、高和严重数量、各类覆盖情况。
- 策略：查看内置模板，维护本项目策略。内置模板不可改。未开放的攻击类策略不能启用。
- 用例：看到目标接口、基线、策略、变异、级别、状态和最近结果。可以查看变异详情、启用、停用、确认高风险、单条执行和批量执行。
- 发现：看到级别、标题、接口、证据和状态。可以确认、标误报、忽略、解决。不提供转缺陷按钮。

生成计划是一个对话框：选择用例或接口，勾选策略，先显示预计条数和每条会做什么，用户勾选后才保存。

变异详情必须同时给出基线值、变异方式、期望、实际结果和结论。不能只显示「安全测试失败」。

## 8. 验收场景

1. 认证。正常请求带有效 Token 能成功。去掉 Token 后如果仍返回 200，结果是疑似问题，并生成高级别 Finding。期望写明 401 或 403。
2. IDOR。用户 A 的 Token 访问用户 B 的任务。返回 403 或 404 为通过。返回用户 B 的任务内容为严重 Finding。没有用户 B 的 Fixture 时，结果是无法下结论，不能猜一个任务 ID。
3. 跨项目。当前用户改用另一个被测项目的资源。返回 403 或 404 为通过，返回 200 为高级别 Finding。使用的是 Fixture 里的业务项目，不是平台项目 ID。
4. 参数。必填整数自动生成删除、空、字符串、负数、0 和超界值。返回 400 或 422 为通过。返回 500 为中级别未处理错误。没有 Schema 时不生成这些变异。
5. 重放。同一创建或支付请求重复两次。第二次产生新的业务 ID，且业务要求幂等，则为疑似问题。未做高风险确认时，请求不发出。
6. 业务状态。已成功的任务再次执行。被拒绝为通过。仍返回成功为疑似问题。没有终态 Fixture 时不硬跑。
7. Agent。用户说「检查创建任务接口有没有越权」。系统选中该接口和授权、IDOR 策略，展示计划后停下。用户确认后才出现安全用例。再确认后才执行。结果进入报告安全摘要。

另外必须通过：

- 项目之间互相看不到策略、用例和 Finding。
- viewer 不能生成用例，member 不能修改策略和 Finding 状态。
- 生产环境和非白名单地址不会发出请求。
- 基线失败不会继续变异。
- 同一疑似问题重复执行不会产生多条未关闭 Finding。
- 原有功能用例、报告和 Agent 的旧意图仍然可用。

## 9. 实现顺序

按开发计划的 Phase A 到 G 串行实现，不要跳步，也不要并行改同一批文件。

1. Phase A：安全数据表、策略和规则、项目环境开关、内置模板。
2. Phase B：变异引擎，以及认证、参数、Header、方法。
3. Phase C：授权、IDOR、换用户、换项目。
4. Phase D：重放、重复提交、业务状态、跳步计划。
5. Phase E：接入用例执行、Fixture、Mock、Finding。
6. Phase F：Agent 和报告摘要。
7. Phase G：前端和七个验收场景。

开工前确认数据库迁移 head 已是 Mock 的 `0010`，并且工作区里没有未提交的 Mock 改动。安全迁移使用 `0011`，不修改旧迁移。

每个阶段完成该阶段的测试后再进入下一阶段。全部完成后运行后端全量测试，以及前端类型检查和构建。

## 10. 完成定义

满足下面全部条件才算 Phase 1 完成：

- 安全用例走现有 TestRun，没有第二套执行器。
- 七个验收场景有自动化测试；页面场景在浏览器里走过预览、确认、执行、查看变异、处理 Finding 和查看报告。
- 生产环境保护、出站白名单、脱敏、项目隔离和高风险确认都有测试。
- 预留的注入、上传、SSRF 等类别无法执行。
- 非安全用例的原有测试仍然通过。
