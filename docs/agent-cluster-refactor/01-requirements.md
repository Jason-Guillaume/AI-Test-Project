## 目标与实施原则

将平台扩展为以任务组织工作的智能体平台。每个任务拥有独立的主 Agent、规划会话和按需启动的专业 Worker，各管理页面继续提供原有的资产查询、编辑和执行入口。

核心结构：全局助手负责接收请求与跟踪任务；任务内主 Agent 负责目标协调；Planner 产出结构化方案；Worker 调用受控工具完成子任务；报告 Agent 汇总结果。确定性的调度器负责领取、依赖检查、状态转换、并发与重试。

实施原则：

- 保留接口、业务流程、测试资产、Fixture / Mock、测试计划、执行记录、报告、安全测试、Web UI 等模块及既有路由。
- 业务数据继续由原有服务管理。新任务保存业务资源引用、来源与版本，不复制第二套用例和报告主表。
- 每个任务独立配置和上下文。相同 Agent 模板可以在不同任务中创建独立实例。
- 用户可直接在管理页面操作，也可从页面选中资产创建智能任务；两种入口使用同一套业务服务和权限。
- 沿用现有 FastAPI、PostgreSQL、SQLAlchemy、React、antd、React Query 与 LangGraph。第一阶段不引入新的智能体框架或外部消息中间件。
- 逐阶段交付真实可运行链路；未完成能力明确显示“未接入”。

## 概念与职责边界

| 概念 | 含义与关系 |
|---|---|
| Task（统一任务） | 用户希望完成的一次工作，包含项目、目标、范围、环境、输入文件、验收条件和预算 |
| TaskRun（任务运行） | 某次启动形成的执行版本；重新运行产生新记录，历史状态与产物保留 |
| OrchestrationPlan（编排方案） | 任务内子任务、职责、依赖与预期产物，经过版本化；与已有 TestPlan 区分命名 |
| WorkItem（子任务） | 可以被独立分派、校验结果和重试的工作单元；使用有向无环依赖图 |
| AgentDefinition（智能体模板） | 可复用的角色、指令、模型、Skills、工具、资源限制与输出契约 |
| AgentInstance（任务参与者） | 某个 TaskRun 中的角色实例，绑定不可变配置快照，拥有独立会话 |
| Worker | 承担专业执行职责的 AgentInstance；可以先后完成多个允许范围内的 WorkItem |
| AgentAttempt（执行尝试） | 一次可追踪的执行段，记录输入、调用、输出、预算消耗及失败原因 |
| TestPlan / TestRun | 原有测试计划与执行记录，通过资源引用与统一任务关联，不合并概念 |
| SystemEvent | 系统实际发生的调度、重试、资源与错误事件；并非一个假装思考的“系统 Agent” |

全局助手与任务内主 Agent 使用不同会话：全局助手通过任务工具创建、查询和发送指令；每条任务的主 Agent 只操作其绑定的项目与任务。全局队列可聚合可见项目，第一阶段每个任务仍归属一个项目。

## 每个任务的智能体团队

| 职责 | 主要输入 | 输出 | 工具边界 |
|---|---|---|---|
| 任务主 Agent | 用户目标、任务状态、Worker 摘要 | 澄清问题、协调指令、调整建议、最终交付说明 | 任务管理与查询；不能绕过调度器直接改变运行状态 |
| Planner | 需求、选中资产、环境、允许能力 | 结构化子任务、依赖、验收条件、专业角色选择 | 以只读查询与提交方案为主；不执行测试 |
| API Worker | 接口/用例引用、测试范围 | 用例草稿、测试执行引用、异常摘要 | 已授权的接口资产、用例和 API 执行工具 |
| UI Worker | 页面对象、已确认用例、目标与登录态引用 | UI 用例草稿、步骤结果、截图/Trace 引用 | 既有 Web 服务和受控浏览器工具 |
| 安全测试 Worker | 已授权目标、策略和确认记录 | 扫描任务引用、Finding 与证据摘要 | 既有安全工具；扫描继续通过原有人类确认规则 |
| 质量审阅 Agent | 子任务交付、验收条件 | 通过/缺失项/返工建议及依据 | 只读证据；建议由主 Agent 接收，预算内创建返工子任务 |
| 报告 Agent | 各 Worker 的结构化结果 | 关联原有报告的汇总、证据索引和未完成项 | 生成报告工具；通知发送继续通过原有确认入口 |

职责预设可以按任务模板组合。每个任务都有独立主 Agent；Planner、专业 Worker、审阅与报告按实际需要创建。简单查询不强制运行全部角色；无安全目标的任务不启动安全 Worker。即使某个角色未启动，会话列表也应说明“未启用”或不展示，不能伪造运行记录。

首个组合：主 Agent + Planner + API Worker + 报告 Agent；第二个组合加入 UI Worker；质量审阅角色在真实证据与返工协议稳定后接入。

## 文件处理

文件采用受控存储标识，不接受服务器任意路径；上传、解析与供 Agent 引用是三个分开的状态。

首批支持文本、Markdown、JSON、CSV 和接口定义等易于受控解析的格式；后续按用户文件场景加入 PDF、DOCX、XLSX 与图片。每种格式分别声明支持范围、体积限制、解析器和验收样例；解析失败可重试并显示原因。

解析在后台执行，产出可按页/章节/表格定位的内容块。模型按任务检索必要片段，保留来源引用；不默认把整个大文件塞入每个 Worker 上下文。文件内容作为业务数据处理，不能覆盖系统指令、权限或确认条件。

上传文件绑定用户、项目、任务可见性与保留策略。重试解析不重复创建附件引用；删除文件时明确关联任务的可追溯影响。首期不依赖独立向量数据库。

## 建议采用的初始决定

1. 每个任务独立团队与会话；全局助手通过任务工具协调，不共享所有任务的完整上下文。
2. 初期每个任务只归属一个项目，全局列表聚合可访问项目。
3. 固定主 Agent / Planner / 专业 Worker / 报告组合先落地，再开放自定义模板与协作派生。
4. 使用 PostgreSQL 持久化调度与游标事件查询，沿用已有技术栈。
5. 同时支持 UI 与 API 的既有业务服务，先完成 API 闭环，再接入浏览器与安全资源。
6. AI 起草配置形成可校验草稿；工具获得执行能力必须经过真实接入和既有授权机制。
7. 原管理页面与原业务数据模型继续作为平台资产的唯一事实来源。

这些决定构成建议实施基线，可在 P0 中调整；调整需要同步任务契约、验收条件和后续阶段范围。
