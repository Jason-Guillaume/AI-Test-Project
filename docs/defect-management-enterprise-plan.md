# 缺陷管理优化方案（无指派人）

平台由测试团队使用，开发人员不进入平台。缺陷以项目为归属，通过状态队列跟进。测试成员从队列打开缺陷，记录观察到的事实、外部处理反馈和回归结果。报告人、实际操作人由系统自动记录，仅用于溯源。

## 一、现状与调整范围

当前单条表单有处理人字段，批量表单支持处理人预设，列表接口接受处理人筛选，后端在处理人变更时触发通知。详情已有失败执行关联、回归验证、关闭和退回入口。实施时应同时调整页面、接口和通知，避免页面移除字段后后台仍产生指派任务。[缺陷页面](../frontend/src/pages/console/Defects/index.tsx) · [批量表单](../frontend/src/pages/console/Defects/BatchCreateBugsModal.tsx) · [查询接口](../backend/app/features/defects/router.py) · [写入与通知](../backend/app/features/defects/services/defect_service.py)

| 范围 | 改造要求 |
| --- | --- |
| 单条、批量、详情 | 移除处理人选择、批量默认值、详情展示及相关成员查询。新单自动进入当前项目的待确认队列 |
| 列表与统计 | 移除按处理人筛选和按人计算的待办、工作量；支持按项目、状态、严重度、优先级、版本、更新时间检索 |
| 通知与分享 | 停止新指派通知。内部提醒可按项目订阅；外部分享用于传递问题和证据，外部反馈由测试成员代录即可 |
| 历史兼容 | 保留历史报告人和操作日志；旧处理人值保留在历史数据中，不参与展示、权限或队列计算。新建时允许旧客户端传空值；对显式设置处理人的请求返回明确的字段停用提示。迁移前盘点旧调用方 |

## 二、新增缺陷（P0）

采用禅道式提单顺序。新建页先显示标题和复现信息，再按分类展开技术证据。顶部带入当前项目，主栏依次展示“标题 → 复现步骤 → 实际结果 → 预期结果”，侧栏放分类、环境、影响版本、严重度和优先级。系统填写报告人、创建时间和初始状态。参考[禅道提交 Bug](https://www.zentao.net/book/zentaopms/133.html)。

| 场景 | 提交方式 |
| --- | --- |
| 手工发现 | 标准提单填写标题、步骤、实际与预期；环境、版本支持“待确认”。严重度沿用现有 1 低至 4 严重，优先级用于安排项目处理顺序 |
| 接口缺陷 | 在复现信息之后展开请求方法、地址、请求头、请求体和响应。保留接口现有校验，敏感凭证在采集、展示与分享前脱敏 |
| 失败执行 | 从原执行带入项目、失败步骤、断言及执行链接，允许测试成员补充业务影响。已有关联时提示打开现有缺陷 |
| 批量发现 | 保留纯标题、六列及八列粘贴，支持列映射和行级错误提示。信息较少的记录进入待确认队列，确认问题时补齐证据。延续整批事务和失败保留输入的行为 |

提供保存草稿、提交、提交并继续。连续提单只继承项目、分类、环境和版本。单文件沿用 10 MB 限制；附件部分失败时显示已创建编号，只重试失败文件。服务端用请求键识别创建超时重试，避免重复建单。

## 三、项目队列和验证闭环（P0）

复用现有五个状态。界面可将底层“已修复”显示为“待验证”，使测试人员清楚该条记录仍需回归。每个动作均由具有项目写权限的测试成员执行，记录实际操作人、时间、前后状态和说明。项目成员可以接续操作。

| 队列及动作 | 状态变化 | 操作时记录什么 |
| --- | --- | --- |
| 待确认：确认问题 | 待确认 → 处理中 | 补齐复现证据、确认影响范围及优先级。处理中表示问题已确认，正在跟进 |
| 处理中：登记可回归 | 处理中 → 已修复（待验证） | 填写可回归的版本、构建或环境，并记录反馈来源。例如“测试环境已部署构建 318，可开始回归” |
| 待验证：回归通过 | 已修复 → 已关闭 | 记录验证结论，关联新执行或填写手工回归环境及结果 |
| 待验证：回归失败 | 已修复 → 处理中 | 保留本次验证证据和失败原因，缺陷重新出现在项目跟进队列 |
| 判重、拒绝、重开 | 待确认 → 已拒绝；已关闭或已拒绝 → 待确认 | 判重关联同项目可见主单；拒绝说明原因；重开记录新版本或新证据 |

普通编辑集中修改事实字段，状态通过上述动作变更。服务端统一校验权限、当前状态及记录版本，并将状态与活动事件一并提交。两人同时验证时，后提交者收到最新状态，页面保留其尚未提交的说明。外部协作者即使从未打开分享链接，测试团队仍可独立完成整个流程。若启用已有公开页“已解决”反馈，则记为外部来源并进入待验证，关闭由项目内回归动作完成。

## 四、列表、详情和协作（P1）

| 功能 | 体验及验收要点 |
| --- | --- |
| 工作台 | 默认显示当前项目未关闭的问题。快捷队列提供待确认、处理中、待验证；另设我提交的、已关闭、已拒绝。队列数与同条件列表总数一致，详情返回恢复筛选和分页 |
| 批量操作 | 支持调整优先级、归档及飞书推送。确认框显示项目、跨页选中总数、不可操作数；切换项目清空选择。部分失败返回逐项结果 |
| 详情与记录 | 首屏显示状态、下一步可执行动作和复现信息；详情内聚合证据、附件、关联执行、外部反馈、活动时间线和分享历史。验证可直接复用失败执行上下文 |
| 权限与归档 | 读写按既有项目权限控制，归档、恢复及对外分享单独授权。归档记录保留原因；归档或撤销后校验单条、批次及附件公开访问均已终止 |
| 分享与提醒 | 推送前预览字段、附件、渠道及有效期，默认排除原始请求头和请求体。项目订阅可汇总长期待确认、待验证的记录，直接链接相应队列 |
| 质量统计 | 展示各状态积压、首次确认耗时、待验证时长和回归失败率。回归失败率按期间失败验证次数除以期间全部验证次数计算，并显示样本量 |
| 性能与可用性 | 列表仅加载摘要，请求正文、附件与活动按需加载。压测大项目分页；覆盖键盘填表、错误焦点、空队列、弱网及越权访问 |

## 五、项目模板（P2）

试点后按项目开放字段显隐、默认值、优先级和不同阶段的必填规则。手工、接口、执行来源三种场景共用同一套状态动作。模板发布前预览示例，记录生效范围和版本；模板字段清单排除人员指派。参考[云效项目模板](https://www.alibabacloud.com/help/zh/yunxiao/user-guide/project-template)。

## 六、上线与验收

1. 先在一个项目记录手工、接口和执行来源三类任务的提单耗时，以及确认问题时需补资料的比例。当前结论来自代码静态核查，实际耗时和线上使用频次有待采样。
2. 首期上线无指派提单、项目队列、回归动作和活动记录。新字段采用可空迁移；旧缺陷仍可查看、编辑及验证。项目开关控制界面灰度，停用的指派写入和项目权限由服务端统一约束。
3. 由两个测试账号完成一次验收：甲从失败执行创建缺陷，乙在同项目队列确认问题、登记可回归，甲回归失败，乙记录下一次构建并验证关闭。全程无需选择人员、等待开发登录或触发指派通知。只读成员可以查看，其他项目成员无法访问。
4. 回归检查覆盖无历史处理人及有历史处理人的旧单、旧批量格式、附件失败重试、并发验证、跨页操作和分享撤销。确认表单、筛选、导出或分享字段清单中均无当前处理人。
5. 第二期上线治理与统计，再评估模板配置需求。建议试点以提单耗时中位数相对下降 30%、确认时补资料比例相对下降 25% 为观察目标，按场景记录样本量后决定推广范围。
