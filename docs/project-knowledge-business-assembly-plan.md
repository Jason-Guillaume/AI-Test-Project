> 本文规划项目知识文档管理、Agent 业务草稿生成与人工编辑的协作方式，供产品确认及后续开发拆解使用；对接现有 business、tasks、agent_governance 和 api_catalog 模块。本文不代表功能已实现。
>
> 编制日期：2026-10-28。依据当前工作区定向核查；实施前重新核对相关代码、数据库迁移 head 与并行改动。

> 目录方案于 2026-10-28 统一：知识库归 `backend/app/knowledge/`，Agent 图归 `backend/app/agents/workflows/business_assembly/`，知识/草稿工具归 `backend/app/tools/builtin/`，业务草稿管理仍归 `backend/app/features/business_assembly/`。目录与迁移细则见 [08 共享能力重构方案](agent-cluster-refactor/08-directory-refactor.md)，交给执行 Agent 的需求见 [09](agent-cluster-refactor/09-optimization-requirements.md)。本次修订仅更新设计，不代表功能已实现。

## 1. 目标与范围

将目前逐项创建业务的操作，扩展为“按项目上传文档 → Agent 提取并组装 → 人工预览调整 → 保存到业务管理”。人工可以从零创建，也可以接手 Agent 草稿或继续编辑已保存业务。

本计划中的“业务”指当前业务管理模块：业务域、流程、动作步骤、前置条件、输入输出变量、业务状态、变量引用、业务规则、接口绑定和参数映射。测试用例、Mock、安全策略等其他平台资产，可在这条链路稳定后按同样方式扩展，不在首期一并生成。

首期交付标准：选定项目和知识文档，输入“根据订单需求组装下单及取消流程”，即可获得有来源依据、可编辑、有缺失提示的业务草稿；确认后进入现有业务管理页面。

## 2. 当前基础与差距

| 已核对能力 | 代码依据 | 实施结论 |
|---|---|---|
| 人工业务编排与子配置编辑 | `frontend/src/pages/console/BusinessManagement/` | 保留入口，复用表单和编辑组件 |
| 业务实体、完整流程读取和写入校验 | `backend/app/features/business/schemas.py`、`services/` | 生成结果适配现有模型，不另造正式业务体系 |
| Agent 业务只读工具 | `backend/app/features/agent/tools/business_tool.py` | 可复用查询服务；需要新增受控草稿生成与保存能力 |
| 持久化任务、Worker、事件、资源回链 | `backend/app/features/tasks/` | 扩展业务组装任务类型，复用任务基础设施 |
| Agent、Skill、模型与工具治理 | `backend/app/features/agent_governance/` | 扩展业务组装工作流及实际运行节点；仅登记工具名称不会使工具可执行 |
| OpenAPI / Swagger / Postman 结构化导入 | `backend/app/features/api_catalog/parsers/document_parser.py` | 接口规范复用已有解析器；普通业务文档需要新增解析链路 |

已确认的约束：

- 当前 `TaskCreate.task_mode` 只有测试执行和 Web 编写；新任务类型还需调整环境必填等执行专用条件，不能将知识组装硬塞入测试执行流程。
- 当前业务新增动作仅接受 `NORMAL`，执行器支持顺序动作。文档中的判断分支、循环、人工等待应标注为待人工处理，或拆成独立顺序场景，不生成无法执行的节点。
- 现有业务创建服务包含内部 `commit()`。批量保存需先提炼共享校验与不提交的内部写入方法，由聚合服务统一控制事务，不能循环调用现有提交型服务来宣称原子保存。
- 当前定位范围内未发现可直接复用的项目知识文档、通用分块检索和业务组装草稿模块。历史架构文档中的拟建模块不作为已存在能力使用。

## 3. 页面与使用方式

### 3.1 项目知识库

在用户控制台新增“项目知识库”，跟随现有组织、项目切换。项目成员可以上传、维护和使用有权限的文档，无须成为平台管理员。

页面包含文档列表、分类、版本、启用状态、解析进度、失败原因、正文预览、来源定位及“基于所选文档组装业务”按钮。分类首批使用需求说明、业务流程、接口说明、字段字典、业务规则。

平台管理端负责文件配额、解析能力开关、任务并发、模型授权和运行异常查看；项目内容仍沿用现有项目授权。Agent 的通用操作指令放在 Skill，项目业务事实放在知识库，两者分别维护。

### 3.2 业务管理保留两种入口

- **手动组装**：沿用当前新建业务域、流程、步骤和配置的窗口。
- **Agent 组装**：选择文档版本、目标业务范围、接口目录范围，提交生成任务。

两种入口最终写入同一套业务实体。Agent 生成并保存的流程能够像手工流程一样打开、修改和补充；人工改动不自动写回原文档或覆盖知识库事实。

### 3.3 草稿工作区

建议采用左侧流程树、中间业务编辑区、右侧文档依据及问题列表的布局。复用现有变量、规则、状态和绑定表单，增加草稿数据适配，避免组件一编辑就直接修改正式资产。

每个流程及关键配置展示来源文档、章节或页码；Agent 推断与文档明确陈述分别标识。用户可改名、调整顺序、删除步骤、修正变量、手工选择接口、补充规则，或针对选中流程要求重新生成。

草稿顶部展示“待补充”“校验失败”“可保存”等状态；保存后返回业务管理中的对应流程，并提供来源任务回链。

## 4. 文档接入与知识处理

首期目标格式为 Markdown、TXT、DOCX、文本型 PDF；OpenAPI / Swagger / Postman 的 JSON、YAML 通过现有结构化解析器处理。DOCX、PDF 解析依赖需在实施时验证与当前运行环境的兼容性，再锁定依赖。

扫描 PDF、截图、复杂表格、旧版 DOC、加密文件与压缩包不纳入首期自动理解范围；解析为空或结构丢失时显示明确提示，不能把空文本视为解析成功。

处理过程：

1. 上传时绑定项目、记录文件摘要和文档版本，校验格式、大小、文件名与配额。
2. 文件保存到受控存储，后台解析正文、标题层级、段落和表格；PDF 保留页码，其他格式保留章节及段落定位。
3. 按章节与业务语义分块，保留原文定位、上下文标题和文档版本。
4. 形成文档目录、业务主题索引及待识别章节清单，供提取任务使用。
5. 版本处理成功后启用；新版本解析失败不影响上一可用版本。相同项目内重复上传同一文件提示复用或新增版本，不静默重复导入。

首期利用现有 PostgreSQL 保存元数据、正文分块和检索索引；先实现项目过滤、关键词及章节检索。检索服务保留替换接口，后续以实际召回评估决定是否加入向量检索及独立索引设施。

**完整组装不能只依赖检索出的少量片段。** 对用户指定的目标文档，先逐章节提取业务候选，再汇总并检索补充细节；超大文档分批处理，记录已覆盖、未覆盖与失败章节。不得把局部检索结果描述成整份文档的完整业务覆盖。

## 5. Agent 组装工作流

新增 `BUSINESS_ASSEMBLY` 任务模式，与现有执行任务共用运行记录、事件和控制命令；业务组装不要求测试环境，也不自动启动测试。

| 步骤 | 输入及产出 |
|---|---|
| 选择范围 | 固定项目、文档版本、目标章节、生成目标及可匹配接口集合 |
| 提取业务 | 按章节识别业务域、角色、流程、动作、变量、状态、规则及证据 |
| 归并组装 | 合并重复概念，生成顺序流程、动作键、变量引用和规则归属 |
| 匹配接口 | 按名称、方法、路径、描述和字段查找当前项目真实接口，提供候选与匹配依据 |
| 确定性校验 | 检查结构、字段类型、引用、顺序、接口归属、参数路径和必填项 |
| 生成草稿 | 保存结构化结果、来源、覆盖清单、歧义及待补充问题 |
| 人工调整 | 用户在草稿中编辑或按范围重新生成，所有改动形成版本 |
| 确认保存 | 服务端重新鉴权、校验版本与完整性，在事务内写入选定流程并回链 |

关键生成规则：

- 文档没有的接口 ID、字段路径、状态值及业务限制不能补造成确定事实。推断项必须标识并可由用户确认或删除。
- 没有可靠接口匹配时保留未绑定动作，形成业务草稿；不因为接口缺失而丢掉整个业务流程。
- 接口匹配必须限制在本项目当前可见目录中；文档包含接口规范时，先走已有导入预览、确认和去重流程，再引用真实接口。
- 校验变量先定义后引用、输出到输入的类型兼容性、唯一动作键与字段映射。现有不能执行的文字规则保留为说明，不标为已执行断言。
- 模型只返回允许的结构化业务数据；文件内容作为业务资料输入，不获得修改权限、批准任务或执行脚本的能力。
- 保存业务默认设为 `DRAFT`。允许保存未绑定但结构合法的业务；“可保存”与“可执行”分别展示，后者还需满足既有执行器条件。

## 6. 人工修改、冲突与更新

首期采用“新建流程或另存副本”，避免自动覆盖现有人工资产。同名流程提示复用候选、改名或跳过，由用户选择。

草稿按修订号保存，人工编辑、重新生成和确认均关联确切修订号；修改后旧校验和确认立即失效。人工修改字段加来源标记，重新生成保留原版本，先展示差异再由用户选用。

保存前对目标业务域、被复用资源和接口结构做快照比对。现有流程的单一版本字段未必覆盖全部子配置变化，后续增量合并应使用完整配置摘要或统一修订机制，不能只比较流程标题或版本号。

知识文档更新后先生成差异提示，第二期支持按影响范围重新生成。已保存业务保留当时依据；旧文档停用后不再用于新任务，尚未确认的草稿需重新选择有效版本再生成或校验。文档删除同步清理可检索内容与缓存，历史引用只保留必要审计元数据；已保存业务不级联删除。

|---|---|
| `app/knowledge/`（拟新增） | 项目知识库、文档版本、受控存储、解析作业、正文分块、索引、只读检索及来源读取 |

| `app/agents/assembly/`、`app/skills/` | 解析并冻结知识范围与 Skill 版本；Skill 提供方法，知识库提供项目事实 |
| `app/features/business_assembly/`（拟新增） | 生成契约、草稿修订、来源证据、确定性校验、人工编辑、预览与保存协调 |
| `app/features/business/` | 提供公开的聚合写入服务，复用现有领域校验及执行约束 |
| `app/features/tasks/` | 新模式、持久化输入快照、生成任务调度、取消/重试边界、回执与产物回链，不持有知识解析或组装图实现 |
| `app/features/agent_governance/` | 保留治理聚合接口；真实工作流登记归 agents，工具登记归 tools，Skill 管理归 skills |
| `app/features/api_catalog/` | 复用格式解析、接口检索及导入预览，不复制接口主表 |

表中路径相对 `backend/`。若当前执行分支已经包含知识库或业务组装，实现迁入对应目标包并保留数据；否则按本计划新增，不建立 `features/knowledge/` 与 `app/knowledge/` 两套实现。解析 Worker 属于 knowledge；生成任务的生命周期属于 tasks，生成图属于 agents。

最小实体建议：

| 实体 | 主要内容 |
|---|---|
| `knowledge_base` | 所属项目、名称、说明、启用状态；首期默认每项目一个，可分类管理 |
| `knowledge_document` / `knowledge_document_version` | 文档逻辑身份、版本、文件摘要、存储引用、解析状态、创建人 |
| `knowledge_chunk` | 文档版本、章节路径、页码或段落定位、正文、检索字段 |
| `knowledge_parse_job` | 持久化排队、尝试次数、租约、失败信息及解析器版本 |
| `business_assembly_draft` / revision | 项目、任务运行、固定输入版本、结构化草稿、修订号、校验结果、覆盖清单 |
| `business_assembly_source_ref` | 草稿修订与字段路径对应的文档片段、引用类型及确认状态 |
| `business_assembly_application` | 确认人、修订号、幂等键、配置摘要、正式业务 ID 映射及保存回执 |

首期结构化草稿和候选项可使用版本化 JSON，正式资产仍写入现有业务表。新增表使用显式 Alembic 迁移，不修改历史迁移。

## 8. 接口草案与一致性

以下为待开发契约，统一使用 `/api/v1` 前缀、现有分页、鉴权和错误信封：

| 接口 | 用途 |
|---|---|
| `GET/POST /projects/{project_id}/knowledge-bases` | 项目知识库列表与创建 |
| `POST /knowledge-bases/{base_id}/documents` | 上传并创建解析作业，返回文档版本与作业引用 |
| `GET /knowledge-documents/{document_id}/versions` | 文档版本、解析状态及失败原因 |
| `GET /knowledge-document-versions/{version_id}/chunks` | 正文预览与依据定位 |
| `POST /knowledge-document-versions/{version_id}/commands` | 重试、启用、停用等受控状态变更 |
| `DELETE /knowledge-documents/{document_id}` | 删除文档并撤出检索 |
| `POST /projects/{project_id}/tasks` | 扩展接受 `BUSINESS_ASSEMBLY` 及知识输入，不强制测试环境 |
| `GET/PATCH /business-assembly-drafts/{draft_id}` | 获取草稿、带修订号编辑 |
| `POST /business-assembly-drafts/{draft_id}/validate` | 校验指定修订并返回可保存、可执行情况 |
| `POST /business-assembly-drafts/{draft_id}/apply` | 确认具体修订和流程集合，保存并返回真实业务引用 |

一致性要求：

- 解析与生成在持久化后台任务中执行，请求不等待长模型调用；页面关闭后继续，按事件游标查看进度。
- 文件写入先暂存，再登记元数据；失败清理孤立文件，解析产物按文档版本和解析器版本幂等保存。
- MVP 限制单次流程和动作数量，对用户选中的可保存集合进行一次有界事务提交；出错整体回滚，明确失败原因。
- `apply` 以草稿修订、选择集合和幂等键去重，同键不同内容返回冲突；业务记录、ID 映射和成功回执在同一事务提交。
- 外部模型调用不占用长数据库事务。租约失效的迟到结果不得覆盖新草稿；取消后停止后续生成，已经完成的保存通过回执核对。
- 每次检索、来源读取与保存均复核当前用户、项目归属和模型授权；权限撤销后停止新的访问和写入。跨项目缓存按项目及文档版本隔离。
- 文档和模型输入中的敏感值按既有策略脱敏，不把登录凭据、密钥和原始文档全文写入任务公开日志。文件下载走鉴权，不暴露任意本地路径。

## 9. 分阶段实施与工作量

以下为初步工程量估算，包含开发与定向验证，按当前架构复用程度估计；不是交付承诺。假设一名前端、一名后端协作，模型服务可用，文档以可提取文本为主。

| 阶段 | 工作内容 | 预估人日 | 验收产物 |
|---|---|---:|---|
| P0：样本与契约 | 选一个项目的代表性需求、流程和接口文档，整理人工标准答案；冻结草稿结构、页面与能力边界 | 2–3 | 样本文档、标准流程及字段清单、接口契约 |
| P1：知识库 | 文件上传、文档版本、异步解析、分块检索、状态和来源预览 | 6–8 | 在项目内上传并查到可定位的有效知识 |
| P2：生成草稿 | 新任务模式、章节提取、流程组装、接口候选、引用及确定性校验 | 6–8 | 从真实文档生成可编辑、带依据与缺失提示的草稿 |
| P3：人工协作与保存 | 草稿编辑、差异、修订控制、聚合事务保存、幂等与业务回链 | 5–7 | Agent 草稿与手工业务在同一业务管理窗口继续编辑 |
| P4：联调与试点 | 权限、失败恢复、并发编辑、代表样本质量评估、回归及使用文档 | 3–4 | 验收记录和试点反馈 |

MVP 合计约 **22–30 人日**；在契约先确定、部分前后端工作可并行的情况下，日历时间可按 **3–4 周**初步安排，实际取决于团队投入与样本文档质量。

首期不纳入：OCR、跨项目自动共享、复杂分支执行、自动执行测试、自动覆盖已有业务、全平台其他资产自动生成。第二期优先做知识更新影响分析、增量合并、人工字段保护，再根据评估补充语义检索和复杂文档支持。

## 10. 验收与上线方式

首期必须通过的场景：

1. 两个项目上传同名文档，检索、草稿、来源和保存均不能串项目；只读成员不能上传、修改或确认保存。
2. 真实文档能生成与标准答案可比对的业务域、流程、动作与关键配置，每个关键事实能定位原文；未覆盖章节明确展示。
3. 接口缺失、描述冲突、变量类型冲突与不支持的分支均展示待处理项，不编造绑定，不显示为可执行。
4. 用户修改 Agent 草稿并保存后，刷新仍可读；在原有业务管理窗口可以继续编辑。纯手工创建流程完整回归通过。
5. 文档解析失败可重试，任务刷新和页面关闭不丢进度；生成取消或 Worker 重启不重复落业务。
6. 重复点击确认、超时重试仅生成一份正式结果；事务中途异常不留下半成品。旧草稿修订和并发修改触发冲突。
7. 文档更新、停用、删除及用户权限撤销后，新检索和待确认草稿不会继续使用失效来源。
8. 保存仅创建业务草稿，不触发真实接口执行、Web 操作、安全扫描或通知外发；后续执行沿用原有入口和约束。

质量评估在 P0 建立人工标准集，分别统计流程识别覆盖、关键字段正确率、依据有效率、接口候选准确率及用户修改时间，避免只用“模型成功返回”判断效果。建议首期试点目标为同类样本的业务组装人工耗时较现状减少至少 50%，以实测结果验收，不预先宣称达成。

上线先按项目开关灰度开放知识库和 Agent 组装；关闭开关后仍能使用原人工业务管理和读取已保存资产。部署先备份、迁移、启动解析及组装能力，再开放入口。回退优先关闭新增写入并回退代码，保留文档与草稿数据，不直接删除已被正式业务引用的表。

## 11. 推荐实施顺序

先选择一个真实项目，以“需求文档 + 接口目录 → 一个完整顺序业务流程”为最小试点，打通 P0 至 P3。能生成、能解释依据、能手改、能可靠保存后，再扩大文档和业务范围。

后续开发可以按“知识库基础”“生成工作流”“草稿与聚合保存”“联调验收”拆分变更；所有变更遵守仓库编码规范及已有项目权限、迁移、任务恢复和执行边界。
