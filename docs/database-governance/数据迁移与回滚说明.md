## 0085 数据保护边界

0085 会把高于 API 上限的超时写为10800，且没有旧值恢复逻辑。本地库升级前已查询，两个计数均为0。其他环境执行前仍需查询并导出受影响的 ID 与原值，或完成数据库备份：

```sql
SELECT count(*)
FROM automation_integration_config
WHERE default_timeout_seconds > 10800;

SELECT count(*)
FROM automation_project
WHERE timeout_seconds > 10800;
```

迁移前应确认重复 queue/build 检测条件不会命中；0085 本身会在存在重复时抛出异常并回滚整批迁移。还应核对现有 Jenkins 配置、execution 关联和 pipeline ID 长度，确保备份可用于恢复。

## 推荐升级顺序

1. 为目标库做可恢复备份；记录 `alembic_version`、各业务表行数、关键 FK/唯一约束以及两个 timeout 查询结果。
2. 在临时 PostgreSQL 库从 `base` 升级到 `0086`，重复执行 `upgrade head` 验证幂等性；运行迁移集成测试。
3. 在目标开发库执行 `alembic upgrade head`，核对表数、列、约束、超时变化、索引定义和 `alembic_version`。
4. 观察应用日志和核心模块回归，再安排其他环境；生产迁移须单独审批和维护窗口。

## 回滚顺序与限制

- P3索引迁移可从 `0086` 降至 `0085`，仅恢复重复索引，通常不需要降级。
- 若要降到 `0084`，先确认没有 Jenkins 配置、执行记录、密文凭据或长度超过64的 CI 路径；否则 `0085` downgrade 会主动拒绝。
- `0085` 对 timeout 的归一化不可由 downgrade 还原。必须依赖迁移前备份/导出的原值恢复，不能期望 Alembic 自动反向恢复。
- `0083` downgrade 会删除导入审计表及其数据；`0082` downgrade 会丢弃 response_key 信息并改写空 status_code。不要在没有单独审查、备份和授权的情况下执行这些降级。
- 不使用 `stamp` 跳过迁移，不手动 DROP TABLE，不以表数变化替代数据完整性验收。
