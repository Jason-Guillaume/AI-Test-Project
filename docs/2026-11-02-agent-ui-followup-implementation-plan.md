## 3. R1：保留折叠区域中的预设 Agent 配置

入口：`frontend/src/widgets/task-assistant/TaskCreateModal.tsx`。

问题：模板与再次执行会预填 agent_definition_id，但高级设置默认未挂载，该字段未注册到表单。直接提交或更新模板时，validateFields/onFinish 返回值可能漏掉此字段。

要求：

- 表单在高级设置从未展开、展开后收起、保持展开三种情况下，同一配置产生相同请求。
- 使用持续注册字段或验证后从完整 store 按 DTO 白名单构建请求等最小方案；不要无条件把全部隐藏字段透传到后端。
- 新建任务、套用模板、再次执行、更新模板共用一致的提交配置语义。主动清空 Agent 后应提交默认编排语义；切项目/类型后不得残留旧 Agent。
- 保持 Agent 候选查询按需加载。修复字段注册不意味着每次弹窗打开就查询所有高级数据。
- 预设 Agent 已停用或无权限时给出明确错误，不无声回退到默认 Agent。

验收：首次打开并套用指定 Agent 模板，直接提交后请求体和运行快照保留同一 ID；再次执行同样成立；更新模板不清空 Agent。新增组件或浏览器行为测试，不能仅断言工具函数或源码包含字段名。

## 4. R2：修正模型配置阻塞分类

入口：`backend/app/orchestration/tasks/services/inbox_service.py`、`runtime/completion_service.py`、`frontend/src/pages/console/Tasks/TaskDetailPage.tsx`，并核对相关状态显示和统计。

要求：

- 以真实运行状态为准：模型重试耗尽后为 status=PAUSED、stage=WAITING_MODEL。不要为了适配错误查询而把运行状态改成一套新值。
- SQL 分类、计数、返回条目 category、详情下一步文案使用一致语义。普通人工暂停不能被归类为模型配置阻塞；已终结任务不能仅凭旧 stage 被纳入。
- 修复配置后沿用现有恢复操作；恢复或被新运行替代后，待处理记录和计数及时变化，避免反复显示旧运行。
- 修正用例中虚构 status=WAITING_MODEL 的数据。至少一个回归通过现有模型失败处理路径产生真实状态，再读取 inbox 验证。

验收：真实模型耗尽任务出现在 model_blocked 类别，计数准确且能定位运行；普通 PAUSED 不出现；恢复后消失或按新状态展示。允许确定性模型替身，不需要调用外部模型。

## 5. R3：让任务与缺陷创建的失败重试保持幂等

入口：`frontend/src/widgets/task-assistant/TaskCreateModal.tsx`、`frontend/src/pages/console/TestManagement/ExecutionHistory.tsx`，以及任务创建、缺陷来源关联服务。

要求：

- 幂等键绑定一次明确的提交意图和规范化有效请求体，不在每次 mutationFn 执行时重新生成。
- 服务端已落库但客户端没有收到响应时，同内容重试使用同一键并返回原结果；成功后明确发起下一次创建，生成新键。
- 用户改变项目、环境、范围、模板版本、目标或缺陷内容时识别为新内容。对上一请求结果未知的情况保留提示/查询入口，不能把变更内容冒充原请求重试。
- 正在提交时阻止重复操作，但不能以按钮 loading 代替幂等设计。延迟成功响应不得清空另一个项目或新编辑的表单。
- 明确关闭弹窗/路由离开后的处理：若允许恢复原提交，应保存最小恢复标识并检查原结果；若不支持恢复，明确展示结果未知状态及检查已创建记录的入口，不宣称刷新后也具有未实现的幂等保证。不要把敏感表单内容写入持久存储。
- 后端相同键不同有效内容返回冲突，不能返回不匹配对象；并发同键请求只能落库一次。

验收：模拟“第一次服务端成功、客户端超时”，重试后任务、运行或缺陷数量不增加；确认成功后用户主动再次创建可以产生新对象；同键不同内容和并发请求行为正确。

## 6. R4：缺陷验证必须尊重重新选择的环境

入口：`backend/app/orchestration/tasks/services/task_service.py::create_verification_task`、`frontend/src/pages/console/Defects/index.tsx::BugVerificationPanel`。

要求：

- 幂等命中时核对项目、来源缺陷、失败执行、environment_id 等有效输入，不只核对来源。
- 相同键但环境不同应明确冲突，不能返回旧环境任务。
- 前端更换环境/来源后建立新提交意图；对内容不变的失败重试继续复用原键，复用 R3 的语义。
- 切换缺陷时清理上一缺陷的环境、来源和提交状态，迟到响应不能操作当前缺陷。
- 保留现有已修复状态检查、资产有效性校验、前置条件限制和人工审批；不自动关闭缺陷。

验收：环境 A 创建成功但响应丢失，同内容重试返回 A 的原任务；同键改环境 B 返回冲突，新意图选择 B 创建的任务实际环境为 B；切缺陷不残留选择。

## 7. R5：隔离项目切换后的对比、缺陷与分页状态

入口：`frontend/src/pages/console/TestManagement/ExecutionHistory.tsx`、`frontend/src/pages/console/Tasks/TaskInboxPage.tsx`。

要求：

- 当前项目变化或清空时，解除基准/候选运行、自动选择标记、对比分页、证据详情、缺陷关联弹窗及已选缺陷，避免上一项目数据短暂可操作。
- 查询 key 和请求启用条件明确包含项目上下文；结果 project_id 不匹配当前项目时不得展示为当前结果或启用操作。仅加 queryKey 不足以替代清理旧 ID。
- 对比证据链接和缺陷创建使用已验证的来源项目；请求中切换项目后，迟到响应只影响原项目缓存。
- 收件箱切项目时重置页码。类别筛选可保留，但结果与计数必须属于新项目；刷新导致页数缩减时处理越界页码。
- 在页面局部处理，不靠重挂载整个控制台清空所有业务状态。

验收：A 第 3 页→只有 1 页的 B 正确展示第一页；A 对比→B 和 A 请求中→B 不保留旧结果或弹窗；清空项目不继续操作 A 记录；原深链接仍定位正确项目与运行。

## 8. R6：补齐模板读取、编辑与启停流程

入口：`frontend/src/pages/console/Tasks/TaskTemplatesPage.tsx`、`frontend/src/widgets/task-assistant/TaskCreateModal.tsx`、`frontend/src/features/tasks/`、`backend/app/orchestration/tasks/{router.py,schemas.py,services/template_service.py}`。

要求：

- 区分“套用”和“编辑”。停用模板禁止套用，但有写权限的用户可以编辑其配置、名称和说明。
- 按 ID 读取编辑目标，不依赖当前筛选的启用模板列表；缺失/无权限/加载失败分别给出合适提示，不静默打开空白创建表单。
- 如需新增详情 API，遵循现有权限和错误信封规范，避免向无权用户泄露模板信息。
- 模板环境可以不固定；编辑模板不能被创建任务的必选环境规则阻断。
- 编辑停用模板默认保持停用；保存配置和启用动作语义清晰，不能因更新请求硬编码 is_active=true 自动启用。
- 启停不能提交列表中的旧配置全文覆盖别人刚更新的内容；采用专门状态变更或受版本保护的等效方案。
- 保留模板隐私过滤、历史运行快照、失效资产提示与使用时服务端重新校验。

验收：停用模板可完整预填并改名/改说明/改配置，保存后仍停用；启用后可套用；无环境模板可以编辑保存，创建真实任务仍要求环境；旧链接不可用时有明确反馈。

## 9. R7：保护共享模板的并发版本

入口：`backend/app/orchestration/tasks/services/template_service.py`、任务 schema/API 和前端保存/启停请求。

要求：

- 更新与启停带上读取时版本，采用条件更新、版本检查加锁或等效乐观并发控制。仅在行锁内把最新版本加一，不能防止旧表单覆盖新内容。
- 同一模板同一旧版本的两次冲突修改只能有一次成功，另一请求返回明确冲突；前端保留未保存草稿，提示刷新或重新核对，不能无条件自动重试覆盖。
- 配置和启用状态的变更遵循一致的版本规则，停用/重启也应使旧编辑请求失效。
- 审查所有现有调用方和测试，记录请求契约变化；若需要迁移，用增量 Alembic，不修改历史初始迁移。
- 创建任务仍校验模板可用性及版本，历史任务输入快照不变。

验收：两个独立数据库会话以版本 N 同时更新，不产生两份相同新版本和静默覆盖；并发编辑/停用有明确胜出和冲突；前端看到冲突且草稿仍在。

## 10. R8：把 Agent 默认结果改成结构化展示

入口：`frontend/src/pages/console/Agent/AgentWorkspacePanel.tsx`、`AgentPanels.tsx`，必要时抽取同领域展示组件。

要求：

- 对照实际响应契约设计展示，不能猜字段或编造汇总。
- 计划：目标、测试范围、环境、步骤、验收条件等实际可用字段。
- 执行：状态、可用数量统计、耗时、失败摘要和执行/报告入口。
- 分析：结论、已有证据和建议下一步；明确没有数据的字段，未知不显示成 0 或成功。
- 原始 JSON 放默认收起的详情区域，保留既有脱敏约束；大文本可局部滚动，不撑宽页面。
- 对话中的结构化消息同步使用摘要，避免对话和工作区都铺满重复 JSON。普通文本消息保持正常展示。
- 未识别的结构保留可理解的回退和原始详情入口，不因渲染异常丢失结果。

验收：计划/执行/分析各有真实样例，默认无需读 JSON 就能找到结果和下一步；空、部分字段、未知字段、长错误均可用；原始详情按需查看。

## 11. R9：完善中等宽度和小屏工作区

入口：`frontend/src/styles/workspace.css`、Agent 页面及相关局部布局。

要求：

- 大屏以对话加结果为主，会话历史可收起；中等宽度优先收起历史，结果可展开/收起，而非只提供三选一整页切换。
- 小屏允许单栏和面板切换，审核勾选、数量和确认按钮仍在同一结果面板，操作区不遮挡内容或输入框。
- 使用容器实际可用宽度确定布局，保留内层滚动和用户阅读历史时不强制滚动的行为。
- 图标按钮补可访问名称、展开状态和键盘操作；切面板后焦点位置合理。
- 沿用现有主题和样式体系，不引入大范围视觉重构。

验收：在 1440/1024/768/390 CSS 像素视口走通会话→生成→审核→执行→结果；长标题、长错误、大列表均无页面级横向溢出。检查缩放/变宽后选择和输入不丢失，并保存脱敏截图。
