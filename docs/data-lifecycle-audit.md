# 全平台数据生命周期审计与统一回收站设计

审计日期：2026-11-12  
审计范围：`backend/app` 路由、服务、ORM、Alembic 迁移，以及 `frontend/src` 路由、功能 API 和业务页面。

## 结论摘要

- 改造前基线扫描记录 **173 个 ORM 表**、**59 个 DELETE 路由**（48 个文件）和 **74 处 ORM `db.delete` 调用**（48 个文件）。内部 worker 清理、关联行解绑也计入删除调用，不能直接视为用户业务删除。
- 用户账号生命周期改造后的再次扫描发现 **177 个 ORM 表**、**62 个 DELETE 路由**（50 个文件），回收站注册 **37 类资源**。普通删除/清理调用仍须按领域策略判断，不能将路由数量当成功能覆盖数。
- 改造前未发现统一批量删除 API、回收站 API、删除审计查询 API或恢复 API；列表中有少量多选 UI，但没有形成统一批量删除链路。
- 改造前用户可调用的 DELETE 以物理删除为主；`DELETE /task-templates/{id}` 是特例，执行的是停用。项目/用户删除服务还会物理清理其所有权下的数据。
- 改造前没有跨领域统一 deleted 字段或查询过滤机制。服务层的外键、引用检查和权限校验各自实现，隔离及运行任务保护不一致。
- 改造前普通业务删除与执行事实、事件、审计证据混在各自领域模型内。运行记录、审计和执行产物不得因删除配置资产而级联销毁。

盘点通过 AST 提取 ORM 表名及 FastAPI `@router.delete`，并以源代码检索复核物理删除调用。前端核对了 `App.tsx` 路由、`AdminLayout.tsx` / `ConsoleLayout.tsx` 导航、业务 API 客户端和具备列表操作的页面。权限及依赖结论依据对应 Service/Router 的检查逻辑；表级外键、唯一约束以 ORM 定义和当前 0001–0076 迁移为依据。迁移 0061 新增的 runtime trace projection 仅保存任务/运行事实引用与投递状态，按运行证据保护对象处理，不接入普通回收站。

## 改造前功能覆盖矩阵

下表记录 Phase 0 的仓库基线，用于说明改造前各域的删除语义；本轮开发后的覆盖状态另见下方“本轮交付核对矩阵”。

“单删”只记录用户可调用的业务资源 DELETE 路由；配置重置、停用、移除成员或解绑不等于删除。批删按服务端 API 判断，不以 UI 的其他用途多选代替。

| 业务模块 / 资源 | 单条删除 | 批量删除 | 当前语义 | 主要依赖 / 约束 | 恢复与保护判断 |

| 项目 | 有，项目所有者可删 | 无 | 物理删除；管理员用户清理还可能删除其创建项目 | 组织、项目成员、所有项目资产，广泛 FK CASCADE；项目名全局唯一 | 应可恢复；必须先做运行任务、Agent 执行及子资源影响预检，严禁静默级联扩大范围 |

| Web UI 页面对象、自动化用例、认证配置、制品 | 有，页面/用例/认证配置 | 已接入页面对象和复用的测试用例批量删除 API | 页面对象与用例转软删除；认证配置仍按既有撤销流程 | 页面对象被加密 Web 步骤引用、认证配置与用例、Web Agent 会话/执行产物 | 页面对象引用未清理时拒删；页面对象和 Web 用例可恢复；截图、Trace、执行制品及测试运行事实受保护；认证配置待评估敏感字段展示和恢复确认 |

## Phase 1 统一设计基线

### 资源数据与审计分离

采用领域资源自己的 `deleted_at / deleted_by / deletion_reason / deletion_batch_id` 软删除列（或与其兼容的领域字段），而不是只在中心表写 tombstone。原因是测试用例、API 模块等已有唯一约束必须允许重建同名活跃数据；跨表 tombstone 无法可靠改变这些约束。软删除状态不复用 `is_enabled`、`status`、`archived`。

中心回收站记录仅用于统一目录与操作收据：资源类型、原始 ID、展示名、模块、项目/组织、删除人/时间/原因、批次 ID、恢复资格、冲突摘要和保留状态。原实体行及 FK 保留；批次/审计事件单独追加写入，不与实体同删。操作每个资源类型由领域服务授权、校验运行状态、处理依赖，并提供资源特定恢复逻辑，不构造无领域校验的万能删除器。

### 唯一约束、查询及状态

- 每个可软删模型审计所有唯一约束；名称唯一改为仅对未删除行生效的 PostgreSQL 部分唯一索引，恢复时显式预检并返回 409 及冲突资源摘要。普通数据不允许覆盖。
- 所有业务读取和执行前置检查只返回 `deleted_at IS NULL` 的数据；仅回收站服务绕过过滤。用户、任务证据、审计、凭据和临时工作行逐类定策略，不对全部 ORM 模型机械套用相同状态。
- 删除/恢复使用事务与行锁或条件更新保证幂等。批量请求先批量检查可见范围，再逐项独立提交/回执，确保部分成功时可解释；同一批次记录成功与失败项。超大批处理再接入现有任务系统。
- 活跃任务引用会阻止删除其执行输入；不能把删除解释为取消。父资源删除默认不自动扩大到子项：回执列出子资源，用户明确选择独立删除或只删父对象；每个子项分别记账。恢复只恢复所选记录，不递归清除删除状态。

### 权限与 API 契约

- 复用项目/组织现有访问检查：删除/批删在领域内要求项目 editor/owner 或模块规定的管理员；回收站查询/恢复按原资源的项目/组织边界重新授权，防止跨项目/组织枚举。
- 权限分别定义为 `resource.delete`、`resource.delete_many`、`recycle_bin.read`、`resource.restore`、`resource.purge`。平台管理员不自动绕开项目所有权和执行依赖检查。
- 保留各领域单条路由，逐域增加批量路由；通用契约采用批量 ID + reason + 显式级联范围，响应逐 ID 返回 `succeeded` 或 `failed`、错误码和冲突对象。回收站提供筛选/分页/排序、详情、单条/批量恢复、审计查询和管理员永久清理预览/执行。
- 历史 DELETE 路由改成逻辑删除并保留响应码/参数兼容；对于现有“删除其实是停用”端点，废弃 DELETE 名称并迁移前端为显式 disable 操作。

### 恢复与清理

父子关系以 `deletion_batch_id` 和每条资源独立记录管理；删除前依赖检查和影响范围必须返回给调用者，且不能自动删除范围外资源。恢复父资源时仅恢复选择项，对关联依赖逐一核验：不存在、已删除、被变更或名称冲突时返回逐项失败回执，不覆盖正常资源、不丢失软删除记录。

本阶段不设置自动保留到期清理。永久清理单独管理员权限、明确确认、依赖预览、操作审计和文件补偿；运行、审计及合规记录永不随业务垃圾清理级联删除。

## 遗留审计限制

静态仓库审计不能确认生产数据的组织约定、数据库实例的人工创建索引、对象存储实际生命周期规则或运行中的后台 Worker；这些应在部署前通过目标环境迁移状态和配置核实。用户删除/恢复/清理审计及保留期限的默认值必须由实际合规策略确定，本需求规定自动物理清理关闭。当前改造覆盖核心测试资产的一部分，并非用户提出的全部业务模块；不能在剩余领域完成审计、实现、数据库验收与 E2E 之前宣称全平台生命周期目标已经完成。
