# 控制改动规模与运行成本

## 开始设计

从用户可观察的结果出发，找到实际入口、现有实现和相关测试。结合改动目录的 AGENTS.md 和仓库根目录的 docs/coding-conventions.md 判断职责归属。

- 单模块且沿用现有契约的修改，确定验收条件和复用点即可实现。
- 涉及前后端契约、迁移、权限、并发或重试时，先沿真实调用链确认数据归属、失败后的状态及验证方式。动手前简述设计选择；有多种可行方案时，比较实现成本、运行成本和可逆性。
- 先打通一条可验证的业务路径。若关键假设失效、需要新增架构层级或预计超过代码预算，先复核再扩写。仍在任务范围内时自主调整；产品语义或范围需要改变时请用户决定。

## 控制代码量

用户指定硬上限时遵守其计数口径。未指定时，每个可独立验收的行为默认以 **150 行新增手写生产代码** 为复核点。预计超出时先检查能否复用现有服务或组件、去掉重复和推测性设计。仍需超出时，说明额外代码承担的职责并继续完成该行为。

开始时记录相关文件已有改动。按本次实际新增行计数，删除行单列，覆盖新建未跟踪文件；测试、迁移、生成物分别统计。保留可读性、错误处理和必要验证，避免通过压缩代码、拆文件或拆提交规避预算。

## 验证整体性能

先判断请求次数、数据量、并发度或资源生命周期是否改变。对热路径选一个用户能感知的端到端指标，再选一个能解释变化的内部指标。静态文案等不影响执行成本的修改可略过基准测试。

| 改动 | 验证方式 |
| --- | --- |
| FastAPI 列表、聚合或批量操作 | 在相同筛选条件下测接口耗时和 SQL 次数。用两种数据规模检查查询次数是否随记录数增长。 |
| React 页面加载或筛选 | 从用户操作测到结果可用，同时记录请求次数、传输量或渲染耗时。保持构建模式与缓存条件一致。 |
| 后台任务、模型或工具调用 | 相同负载下记录完成时间与每任务调用数；按风险检查队列积压、重试重复执行或峰值内存。 |

优化前取得基线。在相同环境、数据和并发条件下重复测量，注明样本量；小样本报告原始范围。按已有性能预算验收，并关注优化是否把成本转移到了数据库、浏览器或队列。条件不足时写清已测事实、未测指标和复测方法，仅对测到的指标下结论。

## 交付

运行覆盖实际入口的相关检查。对有规模或性能影响的任务，报告生产代码增删量、超出复核点的原因、性能前后数据及测量条件。发生架构取舍时补充原因。
